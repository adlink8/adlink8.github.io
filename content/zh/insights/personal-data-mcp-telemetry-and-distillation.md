## 3. 核心架构：从不可篡改事件流到 L0–L4 知识蒸馏管线

为了解决多端碎片化的问题，系统构建了一条自底向上的 **L0–L4 分层知识资产流水线**：

```
┌────────────────────────────────────────────────────────────────────────┐
│                        L4: MCP Tool 服务与智能闭环                      │
│     (STDIO 协议 · 权限隔离 · 隐私脱敏 · 懒加载工具箱 · Bounded Context)   │
└───────────────────────────────────▲────────────────────────────────────┘
                                    │
┌───────────────────────────────────┴────────────────────────────────────┐
│                  L3: 知识图谱与证据锚定 (Memory Graph)                   │
│     (67 条强类型关系: uses_tool / relates_to / enables · 1,771 Links)   │
└───────────────────────────────────▲────────────────────────────────────┘
                                    │
┌───────────────────────────────────┴────────────────────────────────────┐
│                 L2: 认知本体与知识单元 (Knowledge Units)                │
│ (291 KU: 245 Capability · 21 Tooling · 8 Project · 8 Fact · 7 Preference) │
│       状态机: Candidate ──► Canary ──► Eval ──► Promote ──► Watermark   │
└───────────────────────────────────▲────────────────────────────────────┘
                                    │
┌───────────────────────────────────┴────────────────────────────────────┐
│                    L1: 向量索引与多层降级混合检索                       │
│  (10,996 条 Embedding 向量 · Layered Fallback: Cards → KU → Raw Text)   │
└───────────────────────────────────▲────────────────────────────────────┘
                                    │
┌───────────────────────────────────┴────────────────────────────────────┐
│                   L0: 原始事件单一事实源 (SSOT SQLite)                  │
│       (11,370 条事件 · SHA256 去重 · 0 重复 · 不可篡改追加写日志)         │
└────────────────────────────────────────────────────────────────────────┘
```

### 3.1 L0: 确立单一事实源（SSOT）与确定性哈希

任何高质量的数据系统，基石都在于**不可篡改的单一事实源（Single Source of Truth, SSOT）**：
- **存储载体**：轻量、无服务器依赖、跨平台可移植的 `personal_system.sqlite`。
- **幂等摄取**：为每条原始记录生成标准化指纹（`sha256(source + client_id + raw_payload)`）。在采集 11,370 条跨源事件时，去重机制实现了 **0 重复记录**，确保底层数据绝对纯净。
- **数据契约**：严格区分只读事件流与可变派生状态，原始日志一旦写入仅支持只读查询，杜绝任何下游逻辑污染原始现场。

### 3.2 L1: 10,996 条向量索引与分层检索兜底（Layered Fallback）

对于长文本对话与非结构化日志，纯关键字匹配极易产生漏召回。系统为 10,996 条高价值事件生成稠密向量嵌入，并在检索时采用 **分层渐进式兜底策略（Layered Fallback）**：

$$\text{Query} \longrightarrow \text{Cards (精选摘要)} \xrightarrow{\text{未命中}} \text{KU (知识单元)} \xrightarrow{\text{未命中}} \text{Dialogue (上下文对话)} \xrightarrow{\text{兜底}} \text{Raw Events}$$

这种机制既保证了高频概念毫秒级命中（低 Token 消耗），又能在长尾问题上回溯至最底层的原始证据片段。

### 3.3 L2: 知识单元（Knowledge Unit, KU）状态机蒸馏

事件是流式、易逝的，而**知识单元（Knowledge Unit）** 是静态、高密度的提炼物。
系统当前蒸馏出 **291 个标准知识单元**，结构分布如下：
- **能力画像（Capability，245 个）**：提炼开发者掌握的专项技能栈、框架熟练度与排障模式（如 `linux_perf_profiling`、`fastapi_rag_pipeline`）。
- **工具链洞察（Tooling，21 个）**：记录工具的投入周期与异常爆发（如识别到 2026 年 6 月在 `Hermes` 上单月达 448 次突发调用）。
- **核心事实（Fact，8 个）** 与 **长期偏好（Preference，7 个）**：沉淀开发者的系统环境边界（如 Windows/WSL 路径差异、LF 换行约束、无头模式非交互参数偏好）。
- **项目生命周期（Project，8 个）**：关联主要工程仓库与工作区。

所有知识单元的生命周期严格遵循自动化状态机：

$$\text{Candidate (候选)} \longrightarrow \text{Canary (灰度)} \longrightarrow \text{Eval (评测验收)} \longrightarrow \text{Promote (正式入库)} \longrightarrow \text{Watermark (游标更新)}$$

### 3.4 L3: 强类型实体图谱与证据锚定（Memory Graph）

单纯的知识列表容易形成孤岛。系统引入了 **67 条显式拓扑关系** 与 **1,771 条 `memory_links`**：
- **`uses_tool`（49 条）**：将技能或项目与具体执行工具强绑定（如某 RAG 流程绑定 Chroma 与 FastAPI）。
- **`relates_to_topic`（12 条）**：聚合交叉领域概念。
- **`enables`（2 条）** 与 **`embodies`（1 条）**：刻画前置条件与抽象具象关系。
- **证据反查链路（Evidence Traceability）**：每个知识单元都携带包含底层 `event_id` 的证据数组。当 AI 引用某条知识时，能够随时调取当时产生该结论的原生上下文，彻底消除模型幻觉。

## 4. Model Context Protocol (MCP)：将个人资产接入 AI 运行时

拥有完备的本地数据后，如何让不同 IDE、智能体与外部模型安全地使用它们？

系统基于标准 **Model Context Protocol (MCP)**，实现了 stdio 进程级双向通信服务器，并按职责划分为 6 大领域处理器（Domain Handlers）：

```
personal_knowledge.mcp_tools
├── handlers/
│   ├── data.py          # 基础数据分页、聚合统计与质量报告
│   ├── intelligence.py  # 个人能力画像、近期演变与状态快照
│   ├── decision.py      # 架构决策记录、推荐成效度量
│   ├── proactive.py     # 主动式建议收件箱与度量指标
│   ├── agent.py         # 外部上下文解释与试点用例管理
│   └── orchestration.py # Agent 交互会话生命周期与行动前确认
```

### 4.1 领域工具与轻量级协议暴露

在 MCP Server 中，我们避免将整个数据库暴力暴露给 AI，而是通过精巧的契约工具限制上下文爆炸：
- `stats` / `data_quality_report`：快速获取系统健康度、空值告警与分布摘要，响应仅需几百字节。
- `data_aggregate`：支持多维度分组（如 `group_by_fields: ["source", "service"]`），让 AI 在单次调用内完成趋势分析。
- `search_semantic`：按相关度打分并返回带 `score`、`retrieval_unit` 和 `event_id` 的卡片式结构。

### 4.2 隐私与安全护栏（Privacy Guard）

在本地 MCP 工具与外部 LLM 交互之间，系统内置了严格的脱敏护栏：
- **敏感模式拦截**：自动扫描并脱敏 API Key、个人身份敏感字段、内部文件凭据。
- **只读沙盒（Read-Only Constraint）**：外部 MCP 客户端严格限定为只读工具，严禁外部 Agent 通过 MCP 协议未经确认发起破坏性物理写操作。

## 5. 决策科学：基于证据链与哈希绑定的 GSD 门控机制

在 MCP 暴露的高阶工具中，最具工程价值的是**决策分析（Decision Analysis）**与**项目试点门控（Project Pilot）**。

传统的 AI 辅助编程最大的痛点在于：**模型倾向于直接执行猜测出的解决方案，往往轻视副作用与系统不变量**。

### 5.1 确定性校验哈希链

为了确保决策具备严格的审计与复现能力，系统对每一次决策分析运行均生成双向加密绑定的 Checksum：

```json
{
  "run_id": "dar_b99403661addf15b6e0f2375",
  "binding_hash": "7c1ebceaf775f135f3cdcbaee7035a4193f8b51ddcdbae25aaa6529134eca33b",
  "policy_checksum": "3e745a9f6b670c9a25a667efcf478a96ecfde46a6089c29a4552a12f1139766b",
  "candidate_checksum": "595162220f408959e584b4aaccfce1921aa320fa9a1569a226dc19e9118656ac"
}
```

任何外部依赖变更、提示词篡改或证据链断裂，都会使 `binding_hash` 失效，从而阻断自动化执行。

### 5.2 决策权衡三元组与无动作基线

在系统记录的实际决策案例中（如是否升级 Python 3.14 / Node.js 24 运行时环境），决策引擎强制引入了三个关键要素：

1. **量化权重评估（Weight Matrix）**：
   - **安全性（Safety，权重 0.60）**：核心业务与依赖是否受破坏。
   - **速度（Speed，权重 0.25）**：交付节奏与迭代周期。
   - **可逆性（Reversibility，权重 0.15）**：方案是否支持低成本原子回滚。
2. **无动作基线（No-Action Baseline）**：
   明确评估“如果什么都不做，系统的收益、风险与隐性代价是什么”。避免因为了重构而重构带来的附带损害。
3. **刚性停机条件（Stop Conditions）**：
   提前设定熔断指标（例如：“如果验证发现阻断性兼容报错，立即停止采用并回滚至已知基线”）。

## 6. 工程启示与最佳实践

从这 11,370 条跨越 29 个月的事件与个人系统的持续运转中，我们沉淀出三条核心工程原则：

### ① 个人数字资产的飞轮效应（Flywheel Effect）
会话记录不应是阅后即焚的临时缓存。当把每一次与 AI 的深入排障、重构对话通过哈希去重入库，并经过蒸馏沉淀为知识单元后，AI 将越来越“懂你”的工程习惯与项目约束，真正形成伴随工程师成长的数字孪生。

### ② 协议标准化胜过定制胶水代码
通过拥抱 **Model Context Protocol (MCP)**，本地知识系统无需为 Claude Code、Cursor、ZCode、ChatGPT 等各个工具单独编写插件，一套标准 stdio 协议便可贯通所有现代智能体运行时。

### ③ 证据门控是自主 Agent 可靠性的唯一护城河
给 Agent 最大的自由度，同时给它最严苛的边界约束。让 Agent 在执行前先产出 Why 依据、列出不可逆影响并验证证据链，这才是从盲目试错（Vibe Coding 1.0）迈向工业级自主研发（Vibe Coding 3.0）的关键跨越。
